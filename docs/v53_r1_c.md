## A. storage_permission.dart 逐文件结论（读完即落盘）

### C-01 [P1] 五级回退 L5 无写探针，且路径构造用未校验的 nullable 拼接
- 代码事实：`storage_permission.dart:378-382` L5 分支 `final l5Path = '${(await _appSupportDir()).path}/$fallbackRootDirName';` 之后**直接** `return StorageResolution(path: l5Path, level: 5, probeLog: log)`；全链 L1-L4 均有 `_probeWritable`，唯独 L5 没有。`_appSupportDir()`（:385-393）在 `getApplicationSupportDirectory()` 抛异常时返回 `Directory.systemTemp`，且**不创建** `$fallbackRootDirName` 子目录（`dir.create` 只在拿得到 support dir 时执行，systemTemp 分支直接返回）。
- 违反第 11 条（降级必须有明确触发条件与退出条件——最后兜底反而未验证）、第 9 条（失败必须可观测：L5「成功」无留痕）、第 14 条（文件系统边界必须校验）。
- 用户可见后果：在最需要兜底的场景（公共目录全不可写 + 内部目录 API 失败）下，返回一个**从未验证可写、目录可能根本不存在**的路径；下载 / verbose 日志写入全部静默失败，而设置页显示「已生效 L5」，用户无从知道文件根本没落地。属于「长时间静默错误」。
- 证据等级：**实锤（源码直读）**。交叉核对：`download_provider` / `public_media_store` / `error_logger` 是否对返回值再做 `create` 需 file_read 确认（见交叉核对章节）。

### C-02 [P1] `_lastResolution` 缓存与 L5 分支不更新，`resolveRootMode()` 读到陈旧级别
- 代码事实：`:248-254` `resolveRoot()` 用 `_inFlight` 合并并行探测；L1(`:296-303`)、L2(`:310-317`)、L3(`:330-337`)、L4(`:360-367`) 全部 `return _lastResolution = StorageResolution(...)`，**L5（:382）是裸 `return StorageResolution(...)`，未赋值 `_lastResolution`**。`:394-400` `resolveRootMode()`：`final cached = _lastResolution; if (cached != null) return cached.mode;`。
- 违反第 5 条（状态单一来源：`_lastResolution` 与本次返回的 `StorageResolution` 是两份事实且不一致）、第 16 条（「尚未探测」与「已探测为 L5」被映射成同一个陈旧值）。
- 用户可见后果：设备曾探测出 L1（文件写到 `/storage/emulated/0/TierNanMusic`），随后权限被撤销、再探测落到 L5，UI 通过 `resolveRootMode()` 仍显示上一次的 `root`；用户按旧路径去文件管理器找下载文件，永远找不到。且 L5 分支 `lastProbeError` 被置为「公共目录均不可写，已降级到应用私有目录（L5）」（:381），与 `_lastResolution` 中 L1 的 `probeLog` 互相矛盾。
- 证据等级：**实锤（源码直读）**。

### C-03 [P2] 四重检测矩阵的「第 3 重」名存实亡：_quadrupleCheck 只做 3 项，且提前返回使后续项不留痕
- 代码事实：`:225-243` 注释写「四重检测矩阵全跑（逐项留痕，任一失败即整体不通过）」，实现为 `if (!granted) return false; if (!await _nativeCanWriteRoot()) return false; if (!await _nativeIsExternalStorageManager()) return false;` —— 检测 3（写探针）被移到 L1 分支单独做（`:291-295`），且文档 `:209-214` 自称「检测 3：目录实际写探针」属于矩阵。矩阵实际只有 3 个方法调用；`return false` 短路后其余级根本不跑。

### C-05 [P2] API level 兜底映射系统性错位 1 级，且 Android 9 以下映射错误
- 代码事实：`:438-445` `_apiLevelFromOsVersion`：`if (name <= 9) return name;` 注释写「Android 9 == API 28」，但返回的是 `9`；`return name + 20` 把 Android 10→30、11→31、12→32、13→33、14→34、15→35。实际 Android 10=29、11=30、12=31、13=33、14=34、15=35。注释 `@:433-436` 声称「旧公式 name+19 对 Android 13 算出 32（实际 33）… 改为 name+20（10→30 基准）」——「10→30 基准」本身是错的（10 应为 29）。
- 违反第 15 条（单位/数值精度不容协商，版本名→API 映射是标识符精度）、第 31 条（注释解释「为什么」却给出了错误依据）。
- 用户可见后果：仅在原生 `apiLevel` 通道失败时生效；Android 10/11/12 被各高估 1 级，`needsLegacyWritePermission()`（:449-452）判定 `<29` 时把 Android 9（映射为 9，仍 <29，误判为需要旧权限——恰好结论对但数值错），Android 13 恰好蒙对 33。Android 12 被判 32 仍 `>=29` 走 MediaStore，实际影响有限；但 `isAndroid10Plus()` 与所有依赖 `apiLevel()` 的分支在 ROM 通道异常时口径不可信，设置页若展示 API 级别则显示错误数字。
- 证据等级：**实锤（源码直读 + Android 官方 API 级别常识）**。定级 P2 而非 P1：主路径走原生通道，兜底路径影响面受限。

### C-06 [P2] `resolveStrategy()` / `currentStrategy()` 与 `resolveRoot()` 是第二套独立判定口径
- 代码事实：`:512-520` `resolveStrategy()` 只看 `isAllFilesAccessGranted()` + `apiLevel()` + `Permission.storage.status`，完全不调用 `_quadrupleCheck` / `_probeWritable` / `resolveRoot()`；`:522-531` `currentStrategy()` 同样独立。而类注释 `:57-60` 自称「这是唯一权威的存储权限来源」、规划书 P3 要求单一事实源。

- 证据等级：**实锤（源码直读）**；后果分叉需调用方核对（中-高置信）。

### C-07 [P3] `_probeWritable` 的内层 `try` 与末端 `catch (_) {}` 属于宽泛/空体捕获

- 证据等级：**实锤（源码直读）**。

### C-08 [P2] `probeLog` 归类：数据结构已具备，但 `_lastResolution` / L5 / 静态字段三处不一致导致「全链历史」不完整

## B. permission_gate.dart 逐文件结论（92 行，完整读）

### C-11 [P1] 权限网关存在两套互不校验的判定：`hasStorageWriteAccess()` 用 `currentStrategy()`，`ensureStorageWrite()` 用 `requestStoragePermission()`
- 代码事实：`permission_gate.dart:22-26` `ensureStorageWrite()` → `_service.requestStoragePermission()`（该服务方法 `storage_permission.dart:463-483` 对 `level >= 29` **直接 `return true`**，不查任何授权态）；`:33-41` `hasStorageWriteAccess()` → `_service.currentStrategy()`（`storage_permission.dart:522-531`），只要 `level >= 29` 也返回 `mediaStore`（≠ appFallback）即 true。二者都**绕过了 `resolveRoot()` 的四重检测 + 写探针**。而类注释 `:9-11` 明确写「判定逻辑统一由 StoragePermissionService 提供（唯一权威）」。
- 违反第 5 条（状态单一来源：写前校验 / 只读展示 / 实际根路径三种口径）、第 3 条（契约先行：`ensureStorageWrite()==true` 的契约是「可以写」，但实现保证的只是「API>=29」）、第 4 条（UI 层门卫绕过数据层的权威判定）。
- 用户可见后果：Android 10+ 公共目录被 ROM 限制或外置 SD 只读时，门卫仍返回「可写」，下载模块拿到 `true` 后真正写入才失败；而 `resolveRoot()` 明明已探测出 L4/L5。用户看到「下载失败」却没有前置引导，且诊断页可能同时显示「写入能力：正常」与「生效级别：L5」——自相矛盾。这是「权限网关一坨」的核心实锤。
- 证据等级：**实锤（两个文件源码直读交叉核对）**。

### C-12 [P1] `requestWithPrompt()` 授权失败文案只说「原因」，没有「下一步动作」
- 代码事实：`permission_gate.dart:60-76`：`if (!result.isGranted) { Toast.show(context, reason); return false; }`；`isPermanentlyDenied` 分支 `:68-71` 直接 `await openAppSettings(); return false;` —— **不展示任何提示**。调用方传入的 `reason` 是单一字符串，无重试按钮、无「去设置」入口、Toast 自动消失。
- 违反 PLAN P4「错误态文案统一『发生了什么 + 下一步』结构」、第 9 条（失败必须可观测：永久拒绝分支静默跳走）、第 16 条（「可再次申请」与「必须去系统设置」两种业务事实被压成同一个 `false`）。
- 用户可见后果：用户点「去授权」→ 系统弹窗选了「不再询问」→ App 静默跳到系统设置页，用户不知道为什么跳、也不知道该开哪个开关；普通拒绝场景只看到一闪而过的 Toast，没有可点的重试/设置按钮，流程就此断掉。正是任务书要求的「文案下一步动作」缺失。
- 证据等级：**实锤（源码直读）**；调用点传入的 `reason` 具体内容待设置页/arb 核对。

### C-13 [P2] `requestWithPrompt()` 使用期未校验 `BuildContext` 有效性（异步返回后 Toast.show）

- 用户可见后果：授权弹窗期间用户切走 / 页面被 pop，回来后 Toast 打到已卸载的 context，轻则提示不显示，重则抛「Looking up a deactivated widget's ancestor is unsafe」。
- 证据等级：**实锤（源码直读）**；框架层异常为 Flutter 语义推定（高置信）。

### C-14 [P2] `openSettings()` 与 `requestWithPrompt()` 重复实现「跳系统设置」，且失败处理不一致

### C-15 [P2] `hasStorageWriteAccess()` 把「appFallback」当作唯一失败态，忽略 `directPath`/`mediaStore` 下写探针失败
