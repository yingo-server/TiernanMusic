## 文件 1/7：lib/features/player/data/player_repository.dart（506 行，已读完）

### B-01 P1｜ensureDfid 并发等待者递归自调用，重试计数对等待者不生效
- 事实：:74-84。`_registering` 时等待者 `await pending` 后 `return ensureDfid()` 重新进入函数。若首个注册者失败落库（finally 只清 flag，不写 dfid），每个等待者各自再触发一次完整注册，`_registerRetries` 递增的是**各自首次进入路径**之外的路径（等待者路径进 if 分支前不递增），实际并发 N 个等待者可发起最多 N+3 次注册请求，注释声称「有界」但上界是等待者数量而非 3。
- 违反：第 21 条（写操作防重/有界重试）、第 25 条（重试次数上限必须有据）。
- 后果：注册接口 hang 后网络恢复瞬间并发打注册接口，风控概率上升；失败时所有等待者各自再等一轮，播放启动延迟放大。
- 证据：直接阅读，确定。

### B-02 P2｜resolveUrl 全链路无任何超时分级，直连→kapi 降级串行无上限
- 事实：resolveUrl(:205-241) 直连 `_resolveViaDirect` 失败后整体串行走 `_resolveViaKapi`，后者再对每档音质逐次 `_api.get('/song/url')`（最多 5 档）+ 试听兜底再 5 档。全路径对单次请求超时无本文件控制，依赖 dio 全局配置（本文件不可见），且最坏情形 = 直连全档 + kapi 5 档 + kapi 试听 5 档 ≈ 11+ 次串行请求，无总时限。
- 违反：PLAN P2 目标「NetworkPhase 各自超时(3s/8s/30s)」；第 25 条（无上限）。
- 后果：用户点播放后理论可挂 1 分钟以上无任何阶段提示（本层不产生 UI 反馈，也无超时语义）。
- 证据：直接阅读，确定（dio 全局超时未读，但本层总时限缺失为事实）。

### B-03 P2｜fetchDetail 失败静默返回原 song，仅 debugPrint
- 事实：:155-176。catch 后 `debugPrint`，返回原 song。release 包 debugPrint 无输出，用户拿到的歌曲无时长/封面/权益但界面无法区分「详情失败」与「确实无详情」。

- 后果：详情接口持续故障时线上零感知；UI 无法对「无详情」给下一步动作。
- 证据：确定。降级本身有界（不阻塞播放），但可观测性缺失。

### B-04 P2｜kapi 试听兜底循环 `catch (_) {}` 空吞（:481-485）

### B-05 P3｜直连降级循环无「每档间隔/中断」保护，特殊档直连失败报因文案丢失原始 ssaCode

### B-06 P3｜`canPlay`/`requiresVip` 接受 `Map<dynamic,dynamic>` 无边界校验语义

### B-10 P1｜预热引擎入队条件写反，整条 prefetch 链路是死代码（核心发现）
- 事实：prefetch_engine.dart :100-110 `enqueueSongs` 与 :126-141 `updateUpcoming` 的过滤条件均为 `if (!_requested.contains(song.hash)) continue;`——即**只有已在去重集里的 hash 才会入队**。而 `_markRequested`（:56-63）在本文件内**无任何调用点**，`_requested` 恒为空集 → 两个入口的循环体永不执行 → `_pending` 恒空 → 定时器不启动 → `_prefetchOne` 永不被调用。预热 URL/歌词/封面 JSON 的全部能力实际为零。
- 语义应为「不在集合中才入队」（`if (_requested.contains(...)) continue;`）并随后 `_markRequested`。
- 违反：第 32 条（`_markRequested`/`_requestedOrder`/`_maxRequested` 成无人触达的死代码）+ 第 1 条（职责未兑现）；注释声称的「in-flight 合并由 ResourceCache 兜底」成立，但上游闸门完全失效。
- 后果：PLAN P5「preload 键与实播键命中」无从谈起——预热根本不发生；每次播放均冷启动解析，直连/kapi 全链路延迟集中暴露在用户点播瞬间（用户反馈「大量网络延迟」与此直接相关）。文件头注释宣称的预热职责全部不成立。
- 证据：确定（单文件内完整阅读即可闭环：无任何 `_markRequested` 调用点）。

### B-14 P2｜ensureTranslation 缓存命中分支的 emit 行号语义错误风险
- 事实：:113-127。缓存命中时 emit `LyricTranslationPatch(lyricId, missing.first, [for missing ...])`——patch 起始行是 `missing.first` 且**长度=missing.length**。翻译路径 emit（:172-179）的语义是「从 missing[i] 起、连续 n 行」。若 UI 侧按「startLine + index」连续写回（典型实现），缓存命中路径当 missing 非连续（如第 3、7 行缺译）时会把译文写到第 4、5 行——**译文错行**。而逐批翻译路径 missing[i] 起的批内行也未必连续（missing 含跳行时 i..i+39 与行号连续性无关），两处 emit 都隐含「missing 区间连续」的未声明假设。
- 违反：第 22 条（并发/结构假设必须显式并受保护）。
- 后果：跳行缺译（部分行内嵌翻译的老歌，恰是 F4-30 针对的场景）时译文插错行，且命中缓存时**永久错行**（缓存里是按行号存的 Map，写入端对，UI 显示端错）。
- 证据：逻辑确定（UI 消费端 lyric_view 未读，若 UI 按 patch.lines 逐行对 startLine+idx 写回即成立；读 lyric_view 后定级）。

- 事实：dio 2xx 但 body 为 null 时返回 `{}`，调用方 `res['data']` 得 null 走各自分支——onResponse 拦截器已对 `data == null` reject，但仅当 data is Map<String,dynamic> 判定链之外的 null 才拦；`data is List`（数组响应）或非 Map 类型不拦截直接放行，随后 `get` 返回 `res.data ?? {}` 会把 List 的情况**类型断言崩溃**（`_dio.get<Map<String,dynamic>>` 本身会抛 cast error）。第 13 条裸强转。后果：上游返回数组形态的接口直接抛 TypeError 且无包装留痕。P2 边缘，因 kapi 现有端点未知是否返回数组，记 P2 待实测（第 29 条：未实测不得作为依据，标注未验证）。
