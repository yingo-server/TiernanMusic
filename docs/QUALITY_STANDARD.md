# TiernanMusic 代码质量准则（v3.0 LTS）

> 本文件**只陈述原则，不含代码**。参照 Linux 内核编码文化与大型开源项目（Flutter / Dart SDK /
> Rust std / Go stdlib）的工程标准制定。全部审查与修复工作以此为准，与任何任务书冲突时以本文件为准。
>
> 判定方法：每条问题必须能指回本文件的某一条。指不回的，不是问题。
>
> 共 **32 条**，分八章。

---

## 第一章 设计与分层（原则 1–5）

**1. 单一职责，一个单元只做一件事。**
一个函数、一个类、一个文件都应有且只有一个改变的理由。出现「顺手也把 X 做了」的代码即为设计缺陷。

**2. 显式优于隐式。**
依赖必须由构造参数或注入传入，不得在内部自行构造协作者；副作用必须在签名或名称上体现；魔法值必须有具名常量。隐藏的依赖是测试与替换的敌人。

**3. 契约先行，实现其后。**
每个跨层接口在实现前必须先明确：输入取值范围、可抛出的异常类型集合、失败时的返回语义、是否幂等。契约模糊的地方必然是缺陷滋生处。

**4. 分层单向依赖，不得回流。**
底层不得知道上层。核心层不得依赖任何界面框架、不得引用业务模块。UI 层不得绕过数据层直接触达网络或存储。发现回流即为架构级缺陷。

**5. 状态单一来源。**
同一份事实只能有一处权威存储。同一状态同时存在于内存、持久化、全局变量三处，且在多于一处被修改，即判定为缺陷——它必然最终不一致。

## 第二章 错误处理（原则 6–11）

**6. 禁止吞掉异常。**
任何捕获都必须至少完成一件事：转译为领域异常、记录可检索的日志、返回有明确语义的降级值。完全空体的捕获等于把故障埋进地下，属不可接受。

**7. 捕获必须精确到可处理的类型。**
只捕获自己知道如何处置的异常。捕获一切对象的写法会把语言层面的编程错误一并吞下，使真正的 bug 伪装成业务失败。

**8. 异常契约必须单一且稳定。**
同一层对外暴露的异常类型必须可枚举、可穷尽处理。跨层传播时统一包装为领域异常。回退路径与主路径的异常形态必须一致——否则上游的特定处理逻辑只在一半路径上生效。

**9. 失败必须可观测。**
失败要么产生用户可见反馈，要么产生日志，二者至少其一。静默降级（回退成功但调用方毫不知情）必须留痕，否则线上无法定位、无法统计。

**10. 编程错误绝不进入业务降级。**
类型错误、空调用、越界访问属实现缺陷，必须立即暴露。把它们当业务失败去兜底，会让 bug 永久隐藏并产生错误数据。

**11. 降级必须有明确的触发条件与退出条件。**
降级不是「失败了就换个法子」，而是「在已知条件下切换到已知的次优行为」。触发条件、次优行为、恢复条件三者缺一，即为无原则兜底。

## 第三章 数据与空安全（原则 12–17）

**12. 禁止无依据的非空断言。**
非空断言只允许在**同一函数体内已被证明**非空时使用。跨越函数边界、跨越异步等待、来自外部输入的字段，一律禁止强制非空。

**13. 外部数据禁止裸类型强转。**
网络、本地存储、平台通道返回的数据既不可信任也不可假设形态。必须逐一分支验证类型后再使用。上游一次字段类型变更就会造成未捕获崩溃，这是移动端崩溃的第一大来源。

**14. 所有数据边界必须校验。**
边界包括：网络响应、磁盘读取、深链参数、剪贴板、文件系统、Intent 传递。边界内可以做假设，边界外一律假设为恶意或损坏的。

**15. 单位必须显式。**
秒与毫秒、字节与千字节、本地时间与 UTC、行号与字节偏移——凡是存在两种可能的地方，必须在命名或类型上体现，不得靠注释、不得靠字段名白名单猜测。单位混乱产生的错误往往表现为「差一千倍」，且极难复现定位。

**16. 空集合与缺失必须语义分离。**
「未登录」与「已登录但无内容」、「请求失败」与「确实为空」是不同的业务事实。三者都映射成同一个空集合，界面就永远无法给出正确引导。

**17. 数值与标识符的精度不容协商。**
金额、时长、进度、索引必须选定一种精确表示并全程保持。跨层传递时的隐式截断、四舍五入、字符串与数字互转，都必须显式且可追溯。

## 第四章 并发与生命周期（原则 18–22）

**18. 异步结果必须校验世代。**
一次异步操作在等待期间，其有效性可能已经失效（用户换了歌、换了页、换了账号）。任何在等待之后写入共享状态的代码，必须先确认自己仍是当前有效的那一次。

**19. 互斥闸门必须成对且归属于同一所有者。**
开闸与关闸必须在同一调用栈语义内配对完成，且关闸时必须判断「我是否仍是当前持有者」。无条件的关闸会提前放行后续请求，造成真正并发。

**20. 生命周期必须双向对称。**
凡是申请了资源（定时器、订阅、监听、动画、控制器、句柄），必须在同一作用域内存在对称的释放点。异步回调触及已销毁的对象，必须先确认对象仍然存活。

**21. 写操作必须幂等或有防重机制。**
发送、发布、支付、收藏、删除、上传——凡改变服务端状态的操作，都不得因重试、回退、自动恢复而重复执行。无法做到幂等时，必须有去重键或本地提交锁。

**22. 并发假设必须写明。**
若某段代码依赖「此刻只有一个调用者在跑」，必须在代码中显式声明该前提，并在能保护它的地方保护它。隐式的单线程假设是多线程环境下的定时炸弹。

## 第五章 资源与性能（原则 23–26）

**23. 缓存键必须覆盖全部影响结果的维度。**
用户身份、音质、语言、区域、时间窗——任何会影响结果的输入都必须进入缓存键。缺一个维度就会串数据，而串数据在测试环境通常不可见。

**24. 惰性构建，按需计算。**
长列表必须惰性构建；解析、排序、正则编译、格式化不得发生在每帧路径上。构建函数必须是纯函数，不含 I/O、不含状态变更。

**25. 所有资源必须有上限。**
内存缓存条目数、磁盘缓存体积、并发请求数、重试次数、图片解码尺寸——凡是无上限的，迟早会在低端设备上耗尽。上限必须是常量且有据可依。

**26. 热路径零分配。**
滚动回调、每帧回调、高频事件处理器内不得分配大对象、不得做线性查找、不得触发垃圾回收压力。这类开销在高端机上不可见，在低端机上就是卡顿。

## 第六章 网络与接口契约（原则 27–29，本项目最高优先级）

**27. 接口只走原生网关。**
所有业务接口默认且只能调用服务提供方的原生域名。任何第三方中转网关不得作为实现，仅可作为「尚未移植路径」的显式兜底，且必须在代码中写明原因与清理计划。中转网关一旦成为主路径，项目就失去了对协议的控制权与可测试性。

**28. 调用方式必须逐一实测，不得推测。**
每个端点的请求方法、地址、参数集合、请求头、签名位置与算法、默认参数开关，都必须有实测记录支撑。参数形态错误不会报错，只会让直连静默失败并悄悄落到兜底路径——这是本项目最隐蔽、也最昂贵的缺陷类型，判定为高优先级。

**29. 返回结构必须实测并留样。**
每个端点在**匿名、普通用户、付费用户**三种状态下的真实返回都必须留存样本。成功判定口径不统一（有的看状态码、有的看错误码、有的无状态码直接看数据体），必须逐端点确认。凡涉及「上游返回什么」的结论，都必须可追溯到实测记录；未实测的必须标注为未验证，不得作为依据。

## 第七章 可维护性（原则 30–32）

**30. 命名即文档。**
名称必须表达意图而非实现。缩写只允许出现在已被广泛接受的场景。布尔值以判断词开头。集合用复数。名称与行为不符是最高频的误导来源。

**31. 注释解释「为什么」，不复述「做了什么」。**
能从代码直接读出的不要写。必须写的是：为什么选这个方案、为什么排除另一个、上游有哪些反常行为、这个常量从哪来。历史陷阱与平台怪癖必须记录，否则下一个人会再踩一次。

**32. 死代码零容忍。**
未使用的导入、不可达分支、无人写入的状态、注释掉的实现、仅供"以后可能用"的抽象——全部删除。版本控制会记住它们。遗留半成品是维护成本的主要来源。

## 第八章 审查纪律（方法论，非代码原则）

- **只允许完整阅读源码**：逐行从首行读到末行，不得抽样、不得靠模式匹配下结论。片段无法判断上下文正确性。
- **允许查阅语言规范与官方文档**（Dart SDK、Flutter API），用于确认语义边界。
- **禁止编译、禁止运行测试、禁止安装依赖、禁止克隆仓库**。审查的质量来自阅读与推理，不来自构建产物。编译通过不构成正确性证据。
- **禁止以「建议优化」类无后果陈述充数**。每条问题必须给出：位置、事实、所违背的原则、用户可见后果。写不出后果的，降级或删除。
- **禁止读同期其它报告**，避免锚定，保证独立判断。
- **实时落盘**：读完一个文件即追加结论，不得积压到最后统一写入。

## 附：级别定义

| 级别 | 判定 |
|---|---|
| P0 | 崩溃、数据损坏、重复提交、安全泄露、用户数据丢失 |
| P1 | 核心功能失效或长时间静默错误 |
| P2 | 次要功能异常、边界态错误、性能退化、可访问性缺陷 |
| P3 | 整洁度、命名、注释、轻微体验问题 |

分级纪律：只有能写出「用户可见后果」的才可定为 P1 及以上。

## 第九章 实测纪律补充（2026-11-06 用户口径）

**33. kapi 返回不可作为原生网关的实测依据。**
kapi 中转（`kapi.344977.xyz`）的返回**经过 Node 层包装**（axios 重试/错误聚合/字段裁剪/状态归一），
其成功/失败形态、错误信息、字段结构与原生网关直连**不保证一致**。
排查接口问题必须用 `probe` 脚本直打原生域名（三态 cookie），或在真机日志核对直连请求。
任何「实测发现」若数据来源是 kapi 返回，必须在报告/注释中标注「kapi 包装结果，需原生复核」，
不得据此修改直连参数——kapi 上报 `AggregateError` 之类的 Node 层错误与原生返回无关。
