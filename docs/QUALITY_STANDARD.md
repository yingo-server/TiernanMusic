# TiernanMusic 代码质量标准与鲁棒性要求（v3.0 LTS 审查基线）

> 参照 Linux 内核编码风格与审查文化制定。本文件是全部审查/修复代理的**强制判定依据**，
> 与任务书冲突时以本文件为准。所有审查结论必须能追溯到本文件的某一条。

---

## 第 0 章 审查方法约束（硬性）

### 0.1 只允许两件事
1. **完整阅读源代码**：`file_read` 从第 1 行读到最后一行。**禁止** `grep`/`rg`/正则抽样后下结论；
   抽样看到的是片段，片段无法判断上下文正确性。
2. **查阅 Dart SDK 源码/文档**（`https://api.dart.dev`、`https://dart.dev/guides/language/spec`），
   用于确认语言语义（空安全、异步顺序、`late` 初始化、`const` 提升、协变、`Future` 微任务时机等）。

### 0.2 绝对禁止
- **禁止编译**：`flutter build`、`dart compile`、`dart pub get` 均不得执行。审查不依赖编译结果。
- **禁止运行测试**：`flutter test`、`dart test`。
- **禁止安装任何 SDK / 包 / 依赖**，禁止 `git clone`。
- **禁止修改代码**（审查代理）；修复代理只改任务书指定文件。
- **禁止以"编译通过"作为正确性证据**。编译通过 ≠ 逻辑正确，本审查只判逻辑与契约。

### 0.3 判定标准
每条问题必须给出：
- **位置**：`文件:行号`
- **事实**：代码实际做了什么（引用原文，不转述）
- **契约**：它应该做什么（依据：Dart 语言规范 / 本项目规范 / 上游接口约定）
- **后果**：用户可见的失效表现，或可观测的资源/状态泄漏
- **级别**：P0 / P1 / P2（定义见第 7 章）

无法给出"后果"的条目一律降级为 P3 或删除——**不许写"建议优化"这类无后果陈述**。

## 第 1 章 错误处理与失败语义

### 1.1 禁止吞异常
```dart
// ✗ 禁止
try { await fetch(); } catch (_) {}
try { await fetch(); } catch (e) { /* ignore */ }
```
- 任何 `catch` 必须**至少**做一件事：转译异常类型、记录日志、返回有语义的降级值。
- `catch (_) {}`（完全空体）为 **P1**：故障不可见，线上无法定位。
- 例外：明确注释说明"该失败是可接受的且已有其它路径保证"的（如预取），可保留。

### 1.2 禁止过度捕获
- `catch (e)` 捕获 `Object` 会连带吞掉 `TypeError` / `NoSuchMethodError` 等**编程错误**。
  编程错误必须暴露，不得进入业务降级路径。
- 正确形态：`on ApiException catch` / `on FormatException catch` 精确捕获；
  兜底 `catch (e)` 里必须 `if (e is TypeError || e is NoSuchMethodError) rethrow;`

### 1.3 异常契约必须单一
- 同一层对外抛出的异常类型必须可枚举。跨层传播时统一包装（本项目：`ApiException` 一律包成
  `DioException(error: ApiException)`），否则上层 `on DioException` 会漏捕。
- **P0**：异常类型在回退/分支路径上不一致，导致验证流程、登录态清理、错误提示全部失效。

### 1.4 失败必须可观测
- 失败路径必须有日志或用户可见反馈，二者至少其一。
- 静默降级（回退成功但调用方不知情）必须在日志中留痕。

## 第 2 章 空值与类型安全

### 2.1 禁止无依据的 `!`
- `value!` 仅在**同函数内已证明非空**时允许（前置 `if (x == null) return;` 或 `?? throw`）。
- 跨函数边界、跨 await、来自网络 JSON 的字段一律禁止 `!`（**P1**）。

### 2.2 禁止裸 `as` 强转外部数据
- 网络/本地存储/平台通道返回的数据不得 `as Map<String, dynamic>` / `as List`。
  上游字段类型漂移会直接抛 `TypeError`，属未捕获崩溃（**P1**）。
- 正确形态：`if (raw is Map) { ... } else if (raw is List) { ... } else { 走空值 }`。

### 2.3 JSON 解析必须防御
- 数字字段：`(v is num) ? v : num.tryParse('$v')`，兼容上游把 `int` 改 `String`。
- 单位必须显式：秒/毫秒要写在变量名或注释里，**不得靠字段名白名单硬编码猜测**。
- 列表字段：`(v is List) ? v.whereType<Map>() : const []`。

### 2.4 空集合 vs null 的语义
- 「未登录为 null」和「已登录但为空列表」是**不同语义**，不得都映射成 `const []`（**P2**）。
- UI 需要据此区分「请登录」与「暂无内容」。

## 第 3 章 并发与状态机

### 3.1 异步不可取消的假设
- `await` 之后的代码不等于"请求仍有效"。任何跨 `await` 的状态写入必须校验**世代号/令牌**：
  ```dart
  final token = ++_token;
  final data = await load();
  if (token != _token) return;   // 已作废
  ```
- **P0/P1**：旧请求后完成并覆盖新状态（音频源、当前页、列表内容）。

### 3.2 闸门变量必须成对
- `_loading = true` 必须在**同一个所有者**的 `finally` 中置回，且 `finally` 要判断"我是否仍是当前请求"。
- 无条件 `_loading = false` 会提前开闸，导致两个请求真并发（**P1**）。

### 3.3 生命周期
- `Timer` / `StreamSubscription` / `AnimationController` / `TextEditingController` 必须在 `dispose` 释放。
- `await` 之后操作 `context` / `setState` 必须先判 `mounted`（**P1**）。
- Provider 中建立的订阅必须挂到 `ref.onDispose`。

### 3.4 幂等性
- 写操作（发送、收藏、删除、上传）**不得因重试/回退而重复执行**。
- 判定：失败路径是否会再发一次同样的写请求？会 → **P0**。

## 第 4 章 资源与性能

- 列表渲染必须 `builder` 惰性构建；禁止在 `build` 内做 I/O、JSON 解析、正则编译。
- 缓存 key 必须包含影响结果的全部维度（用户 id、音质、语言），否则切号串数据（**P1**）。
- 缓存不得返回内部可变对象引用（调用方修改会污染缓存）。
- 图片/音频解码尺寸必须有上限，禁止无限制缓存原图。
- 禁止在热路径（每帧、每次滚动回调）分配大对象或做线性查找。

## 第 5 章 网络与接口契约（本项目专用，最高优先级）

### 5.1 必须走酷狗原生网关
- **所有接口默认只允许调用酷狗原生域名**（`complexsearch` / `pubsongs` / `trackercdn` /
  `openapi` / `login-user` / `userservice` / `lyrics` / `gateway` / `ocean` / `musicadservice`）。
- **禁止以 kapi 网关（`kapi.344977.xyz`）作为实现**。kapi 仅允许作为「未移植路径」的兜底，
  且必须在代码注释中写明原因。
- `AppConfig.kugouApiBase` 只允许出现在「回退」与「Cookie 存储」位置。

### 5.2 调用方式必须实测
- 每个端点必须逐字段核对上游参数（method / baseUrl / params / headers / 签名位置）。
- **参数形态错误会导致直连假失败 → 静默回退 kapi**，这才是最隐蔽的功能缺陷（**P1**）。
- 已知易错点：
  - `signature` 必须放 **query**，不是 header
  - `notSign: true` 的端点（`/v5/url`）**不得**补 signature
  - `clearDefaultParams: true` 只允许 5 处已验证端点
  - 版本号必须对齐（`/kmr/v1/audio_group/author` 必须 v1，v2 返回 Map 不兼容）
  - 成功判定不统一：`status==1` / `status==200` / `err_code==0` / 裸 Map

### 5.3 返回必须实测
- 每个端点在**三态**（匿名 / 非VIP / VIP）下的真实返回必须留存样本。
- 审查结论凡涉及"上游返回 X"的断言，必须能指向 `docs/api_verified.md` 的实测记录或本次实测输出。
- 未实测的推测必须标注「未验证」，不得当作依据。

## 第 6 章 架构与依赖

- `core/` 禁止 import `features/**`；`features/*/data/` 才发网络请求；UI 层零直接构造 Repository。
- 禁止循环依赖；禁止在 `core` 层 import UI 框架包（`qr_flutter`、`flutter_svg` 等）。
- 状态管理单一来源：同一份状态不得在 Provider / Hive / 全局变量三处并存。

## 第 7 章 级别定义

| 级别 | 判定 |
|---|---|
| **P0** | 崩溃、数据损坏、重复提交、安全泄露（token/明文 http）、用户数据丢失 |
| **P1** | 核心功能失效或长时间静默错误（登录、播放、搜索、收藏、评论、下载） |
| **P2** | 次要功能异常、边界态错误、性能退化、可访问性缺陷 |
| **P3** | 代码整洁度、命名、注释、轻微体验问题 |

**分级纪律**：只有能写出「用户可见后果」的才是 P1 及以上；写不出的一律 P2/P3。

## 第 8 章 审查产出规范

报告必须落盘，路径固定，实时追加（读完一个文件写一个，禁止最后统一写）：

```
### <文件>:<行号> <一句话标题>
- 级别：P0/P1/P2
- 事实：<代码原文>
- 契约：<依据本文件第几章 / 上游接口 / Dart 规范>
- 后果：<用户可见失效 或 资源泄漏>
```

文件末尾追加「问题清单」按级别排序 + 统计表。
