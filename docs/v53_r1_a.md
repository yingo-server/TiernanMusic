## 3. 实锤问题清单

### A-01【P1｜通知栏「从队列选歌」完全失效，QueueHandler 双轨】
- 代码事实：`audio_handler.dart:25` 声明 `with QueueHandler, SeekHandler`；全文 724 行**没有** `skipToQueueItem` / `addQueueItem` / `insertQueueItem` / `removeQueueItem` / `updateQueue` 的 override（全文检索确认）。`_emitQueue()`（:280-292）只把 `_songs` 映射为 `MediaItem` 推给 `queue.add(...)`；`_broadcastState`（:216-245）`androidCompactActionIndices: const [0,1,2]`、`systemActions` 只含 seek/seekForward/seekBackward，但 `queue` 非空 + `queueIndex` 已下发，Android MediaSession 会暴露队列项。
- 判定：`audio_service 0.18.15` 的 `QueueHandler` mixin 默认 `skipToQueueItem(int index)` 实现为 `throw UnimplementedError`（mixin 契约要求子类 override 手写队列），本项目未 override；同时 `SeekHandler` 与 `TiernanAudioHandler.seek`（:629）重复但无冲突。
- 违反：第 3 条（契约先行：声明了 QueueHandler 能力却不实现）、第 5 条（状态单一来源：媒体会话队列与手写队列双轨）、第 9 条（失败必须可观测：通知栏点击队列项抛未实现异常，仅落平台日志，UI 无反馈）、PLAN §三.6「QueueHandler mixin 弃用（手写队列统一）」的反向实锤——现在既没弃用也没实现。
- 用户可见后果：在锁屏/蓝牙/通知栏媒体控件里点队列里另一首歌 → 无反应或后台抛 `UnimplementedError`，播放列表「跟没有一样」的直接来源之一；Android Auto / 车载 / 耳机媒体键同样不可用。
- 证据等级：A（源码全文 + mixin 契约；`pubspec.yaml:28` 锁定 `audio_service ^0.18.15`，mixin 语义为公开 API 事实）。

### A-02【P1｜队列点击「跳到某一首」执行整表替换并重置队列，且 `_pendingIndex` 指向旧下标】
- 代码事实：`queue_sheet.dart:170` `_play(controller, live, idx)` → `controller.playQueue(live, idx)` → `audio_handler.playQueue`（:295）：`_pendingIndex = null`、清 `_songs`、`_songs.addAll(songs)`、`_emitQueue()`、`await _playAt(index)`。而 `_playAt`（:372-376）在 `_loading == true` 时把 `index` 存进 `_pendingIndex` 并 return。
- 冲突时序：`playQueue` 在 :301 清空 `_pendingIndex`，但若上一首 `_playAt` 仍在 `_loading`（网络解析 20-30s，见 player_repository.dart），新 `playQueue` 走 :325 整表替换 → :378 之前先命中 `_loading` → :374 `_pendingIndex = index`（相对**新队列**）。prev `_playAt` 的 finally（:525-535）把 `_loading=false` 后用 `handoffToken == _playToken` 校验后 `_playAt(pending)`。看似自洽，但 `playQueue` 的 `token`（:299）在 `_playAt` 里又被 `++`（:380）覆盖，若旧请求在 :466 `await _player.play()` 后返回时 `token != _playToken` 就 return；而 `playQueue` 的 :304 校验早已通过，此时**没有新的 `_playAt` 被调用**（旧请求被作废，新请求只留了 `_pendingIndex` 而没有被任何 finally 触发——因为 `_playAt` 从未真正进入它的 try/finally）。
- 违反：第 18 条（异步结果必须校验世代）、第 19 条（互斥闸门必须成对且归属于同一所有者）、第 5 条（跳到队列项语义被实现为「替换整个队列」）。
- 用户可见后果：「点了队列里第 3 首没反应」；或触发一次全队列重灌导致 `updateUpcoming` 重新预取 15 首、`currentSongStream` 重发、mini_player 刷新闪烁；在 `playQueue` 并发窗口内点两首歌会只播最后一首，前一次点击彻底丢失。
- 证据等级：A（源码逐行时序推演，:299/:301/:304/:372-376/:380/:525-535 全链可复现）。

### A-03【P1｜`_index` 在闸门命中前被写，导致「当前歌曲」与「实际声音」长期错歌】
- 代码事实：`_playAt`（:378）先 `_index = index; _emitMediaItem();`，随后 :372 才判断 `if (_loading)`。即：当 `_loading == true` 时，函数**已经**把 `_index` 改成待播下标并发了 `currentSongStream`/`mediaItem`，然后才把 `index` 存进 `_pendingIndex` 并 return（:374-376）。此时引擎里正在播放/装载的是上一首，`_broadcastState`（:239）下一次 tick 会把 `queueIndex: _index`（新下标）与旧的 `processingState/position` 一起推给系统。
- 违反：第 5 条（同一份事实多处不一致）、第 18 条（等待之后写共享状态未确认世代）、第 3 条（`_playAt(index)` 的契约应保证「返回后 index 生效或明确不生效」，实际是「半生效」）。
- 用户可见后果：加载中切歌 → 通知栏/迷你播放器/全屏页立刻显示新歌封面与歌名，但声音仍是旧歌（或静音），进度条按旧歌 position 走；若这次请求最终被 `_pendingIndex` 交接丢弃（见 A-02），UI 永久停在新歌名+旧声音，用户点播放/暂停都作用于旧音源。这是「播放列表跟没有一样」最直观的表现。
- 证据等级：A（:372-380 行序为静态事实，无需运行时）。

### A-04【P0｜`_lastPlayUrl` 资源快照可被错歌「完整播放」污染永久缓存】
- 代码事实：`_setLastSource`（:273-277）在 `_playAt` 在线分支 :460 / 离线回退 :431 写入；`processingStateStream` 的 `completed` 回调（:108-125）用 `_lastPlayUrl` 判定「本曲完整播放」并调 `PrefetchEngine.instance.onPlaybackCompleted(_lastPlayUrl, 'audio', declaredBytes: _lastDeclaredBytes)` 永久入库。该回调**不校验任何世代**，且 `_lastPlayUrl` 是全局字段而非 per-source 绑定。
- 具体路径：_playAt(A) 装载 A 的 URL 成功、写 `_lastPlayUrl=A`，`await _player.play()`（:467）在飞；用户切歌 B 走 `_playAt(B)` → :380 `++_playToken` 作废 A → B 在 :378 已改 `_index`/`mediaItem`，但 B 的 `fetchDetail/resolveUrl` 未完成；此时若 A 的 `setAudioSource`/引擎触发 `ProcessingState.completed`（A 是 60 秒试听且 `_lastIsPreview` 被 B 的 :385-387 重置流程尚未来得及覆盖，或 A 与 B 共享同一 URL），回调会用 A 的 URL + B 的 `_lastIsPreview` 组合判定。更直接的实锤：`_pauseEngineOnly()`（:588）失败分支暂停引擎后 `_lastPlayUrl` **不清空**；用户随后按 `stop()`（:617-620）虽然 `_setLastSource('',0,isPreview:true)`，但 `onNotificationDeleted()`（:716-721）只 `_playToken++`/清 pending/`stop()`，**不** `_setLastSource`——划掉通知后若底层补发 completed，仍会按最后一次 URL 永久缓存。
- 违反：第 18 条（异步结果必须校验世代）、第 21 条（写操作必须幂等或有防重机制：永久缓存写入无去重/无世代键）、第 5 条（资源快照应与 source 绑定而非全局可变字段）、PLAN §三.5「播放链路任何 catch 必须带世代守卫」的同类缺陷（此处是 completed 回调，非 catch）。
- 用户可见后果：试听/错歌片段被当作完整曲永久缓存，离线播放命中错误文件；存储空间被错误音频占用且无清理入口（数据损坏，定 P0）。

## 5. 状态机事件表建议（供重写定案）

### 5.1 单一 sealed state（取代 §2 全表）
```dart
sealed class PlayerState {
  const PlayerState();
}
final class PlayerIdle extends PlayerState { const PlayerIdle(); }
final class PlayerLoading extends PlayerState {
  const PlayerLoading(this.song, this.phase, {this.startedAt}); // phase: resolving/detecting/streaming
  final Song song; final NetworkPhase phase; final DateTime? startedAt;
}
final class PlayerPlaying extends PlayerState {
  const PlayerPlaying(this.song, {required this.isPreview, required this.quality});
  final Song song; final bool isPreview; final AudioQuality quality;
}
final class PlayerPaused extends PlayerState {
  const PlayerPaused(this.song, {required this.reason}); // reason: user/verification/failure
  final Song song; final PauseReason reason;
}
final class PlayerFailure extends PlayerState {
  const PlayerFailure(this.reason, {required this.retry, required this.nextAction});
  final FailureReason reason; // engineNotReady/verificationRequired/resolveFailed/sourceFailed/queueEmpty
  final RetryAction? retry; final String nextAction; // 「发生了什么 + 下一步」
}
```
- 唯一权威存储：`PlayerStateMachine._state` + `QueueState{items: List<QueueItem>, index: int, mode: shuffle/repeat}`；`_songs[_index]` 只允许出现在状态机文件内（PLAN §三.1）。
- 所有派生事实（mediaItem/queue/playbackState/currentSong/preview/quality/error/engineReady）由**一个** reducer 从 state 单向投射，禁止各自 StreamController。

### 5.2 事件表

| 事件 | 载荷 | 前置条件 | reducer（原子） | 副作用（由 adapter 执行） | 失败/退出 |
|---|---|---|---|---|---|
| `PlayQueueRequested` | `items, startIndex, source` | `items` 非空；越界夹到 0 | 新 `generation++`；`QueueState=items/index=startIndex`；`state=Loading(song,resolving)`；清 `pendingVerification`/`failureStreak` | `repository.fetchDetail` → `resolveUrl` → `player.setAudioSource` → `play()`；`updateUpcoming(items,index)`；`mediaItem/queue/playbackState` 一次投射 | `resolveFailed`→`Failure(reason,retry=PlayQueueRequested 同参)`；`verificationRequired`→`Suspended` |
| `PlaySongRequested` | `song, policy: insertAfterCurrent\|append\|replace` | hash 非空（空 hash 拒绝并给 Failure） | 按 policy 生成新 `QueueState`（去重按 hash，不用 `Song.==`）；`generation++`；`state=Loading` | 同上；不整表替换（修 A-02/A-13） | 同上行 |
| `NextRequested` | `manual: bool` | `queue.isNotEmpty` | 计算 next：`repeat==one && !manual → index`；`shuffle → 从未播集合取（有历史）`；`index+1 >= len && repeat==all → 0`；`repeat==off && 到尾 → state=Idle + 明确提示`；`generation++` | `_playAt(next)` | `repeat=off` 到尾必须发 `QueueExhausted` 提示（修 A-06） |
| `PreviousRequested` | — | `queue.isNotEmpty` | `position>3s → seek(0)`（不换 generation）；否则 `index-1`，`repeat==all` 回绕；`generation++` | `_playAt(prev)` | — |
| `SeekToRequested` | `positionMs: int（显式单位）` | `state is Playing\|Paused` 且 `engineReady`；`0<=ms<=durationMs` | 不改 state，仅记 `pendingSeek` | `player.seek(Duration(milliseconds: ms))` | `Loading/Idle/Failure` 直接拒绝并给「正在缓冲，稍后再试」；异常转 `Failure(sourceFailed)`（修 A-23） |
| `Completed` | `sourceId`（与本次 setAudioSource 绑定的资源 id，**不是**全局 `_lastPlayUrl`） | `generation == source.generation` 且 `sourceId == current.sourceId` | `repeat==one → 重播同 source`；否则按 `NextRequested(auto)` 计算 | `onPlaybackCompleted(url, bytes)` **仅当** source 非 preview 且 declaredBytes>0 且校验通过（修 A-04） | 世代不符直接丢弃，不缓存不跳歌 |
| `Failed` | `generation, reason, exception` | `generation == current.generation` | `failureStreak++`；`failureStreak < min(queue.length, 3)` → 发 `NextRequested(auto)`；否则 `state=Failure(reason, retry, nextAction)` | `_errorController` 单一出口；`playbackState.error` 由 state 投射 | 世代不符丢弃；`verificationRequired` 走 `Suspended` 而非 Failed |

### 5.3 落地约束（对应 PLAN §三）
1. `_songs`/`_index`/`_loading`/`_playToken`/`_pendingIndex`/`_pendingSongHash`/`_failureStreak`/`_isPreview`/`_last*` 全部收进 `PlayerStateMachine` 单文件，`audio_handler` 只保留 just_audio ↔ 事件转换（PLAN §二 P1）。
2. `QueueHandler` 二选一：弃用并在 `audio_service` 侧不发布可点队列，或完整 override `skipToQueueItem/addQueueItem/removeQueueItem/updateQueue`；当前「声明但不实现」必须消除（A-01）。
3. UI 只 `watch(playerStateProvider)`：mini_player / full_player_page / queue_sheet 共用同一 `PlayerState → Widget` 映射表，`loading/buffering/error/empty` 四态互斥（A-16、PLAN §二 P4）。
4. 每个异步边界（网络、`setAudioSource`、`play()`、`seek`、`completed`、`verification`）必须携带 `generation` 且回调入口校验；`finally` 只由该 generation 的持有者关闸（第 18/19 条）。
5. 错误文案统一 `FailureReason → {发生了什么, 下一步动作, retry event}`，删除 `'播放失败：$e'` 裸串（A-09/A-21）。
6. `Song` 相等性改为「hash 非空且相等」并让 `hashCode` 与之一致，或全面改用显式 `songId` 值对象；禁止 `indexOf(song)` 依赖 `==`（A-11）。
7. `dispose()` 对称取消全部订阅 + close 全部 controller，或改用单一 `StateController` 由 Riverpod 托管（A-12、第 20 条）。

## 7. 总判定

1. **队列无单一事实源**：`_songs`/`_index` 与 audio_service `queue`/`mediaItem`/`playbackState.queueIndex`、just_audio 引擎、Riverpod 16 个独立流、UI 快照共 5 层，无原子投射，第 5 条被系统性违反（A-01/A-02/A-03/A-16）。
2. **切歌/自动下一首/随机/循环/seek 五条路径均不自洽**：自动下一首忽略 `LoopMode.one`（A-05）、随机下标与 `_index` 不同步（A-06）、seek 绕过世代与三态（A-23）、队列点击实现为整表替换（A-02）、通知栏队列点击未实现（A-01）。
3. **7+ 状态变量互相矛盾**：§2 全表 29 项，`_index` 与媒体会话/引擎 source 三处错位（A-03）、`_isPreview` 与 `_lastIsPreview` 两份试听事实（A-04）、三份错误事实（A-09）、`engineError` 永不清除（A-09）。
4. **通知栏控制与 UI 不同步**：playbackState 无任何 UI Provider（A-16）、随机/循环入口缺席系统侧（A-07）、`onNotificationDeleted` 不清媒体会话（A-10）。
5. **20028 挂起 / 世代闸门 / 失败重试未闭环**：挂起无统一退出事件且可被覆盖（A-08）、`completed` 回调无世代校验（A-04，P0）、`_loading` 与 `_playToken` 双闸门在 `playQueue` 并发窗口可丢请求（A-02）、失败重试不区分装载/解析失败且直接跳歌（A-21）、`_configureSession` 空 catch（A-19）。
